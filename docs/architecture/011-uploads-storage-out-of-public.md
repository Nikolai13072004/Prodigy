# ADR-011: хранилище `/uploads` вынесено из `public/` ради авторизации

## Статус

Принято (2026-08-20).

## Контекст

Файлы курсов (материалы, презентации, медиа тестов, вложения ответов, аватары)
лежали в `public/uploads` и отдавались через роут
[`app/uploads/[...path]/route.ts`](../../src/app/uploads/%5B...path%5D/route.ts).
Предполагалось, что роут — единственная точка выдачи и в нём можно проверять
доступ.

Это не так. В Next статические файлы из `public/` отдаются **раньше**, чем
срабатывает route handler. Проверено на dev-сервере: запрос существующего файла
`public/uploads/x.html` возвращал `Cache-Control: public` и содержимое **без**
прохождения через роут (роут отвечал только на запрос отсутствующего файла).

Последствия, пока корень в `public/`:

- любой анонимный GET по URL отдавал материалы курса — авторизации не было;
- CSP `sandbox`, который роут вешает на `.html`/`.svg`, обходился для реально
  загруженных файлов — то есть stored-XSS через загруженный html не закрывался.

Неугадываемое имя файла (`randomUUID`) — это security through obscurity: утёкшая
ссылка работает бессрочно и для всех.

## Решение

Физический корень области `uploads` вынесен из `public/` в `data/uploads`
(область `branding` осталась в `public/` — логотипы публичны, а исполнение SVG
там закрыто заголовками в [`next.config.ts`](../../next.config.ts), которые
Next применяет и к статике: «checked before the filesystem»).

URL остался прежним — `/uploads/<key>` (`publicBaseUrl`). Меняется только физика:
единственный путь к байтам теперь — через route handler, где стоит проверка
доступа [`canAccessUpload`](../../src/lib/storage/upload-access.ts):

- аутентификация (нет сессии → `401`);
- авторизация по владельцу файла, восстановленному из ключа (нет доступа → `403`);
- связь «ключ → владелец» — по префиксу ключа и полям, ссылающимся на URL
  (`CourseItem.fileUrl`, `Course.coverUrl/thumbnailUrl`, `User.avatarUrl`, медиа
  и вложения тестов в JSON). На эти поля добавлены индексы (миграция
  `20260820_..._add_upload_reverse_lookup_indexes`).

Правила доступа по классам ключа: материалы и презентации (вкл. `presentation_preview`
и пакет `pptx-html5/` по конвенции имён) — доступ к курсу; обложки/интро — любой
аутентифицированный (каталог); аватар — свой или `users.view`; вложение ответа —
загрузивший ученик или менеджер курса; медиа вопроса — доступ к курсу. Дедупликация
даёт один-ко-многим, поэтому доступ проверяется по любой ссылающейся сущности.
Ключ без владельца закрывается (fail-closed).

## Последствия

- Файлы больше не доступны анонимно; XSS-вектор через загруженный html закрыт
  (нет статической выдачи в обход роута).
- Каждый запрос `/uploads/*` стоит запроса-владельца в БД (индексирован для полей,
  LIKE по JSON для медиа/вложений тестов — реже).
- Точки, читавшие `public/uploads` мимо storage-абстракции, переведены на
  `storage.rootPath("uploads")` (`course-creation-actions.ts`,
  `get-course-presentation-previews.ts`).

## Тома docker: вложенное монтирование

В обоих compose область теперь монтируется как `lms_uploads:/app/data/uploads` —
**поверх** `lms_data:/app/data` (вложенный том). Docker монтирует `lms_data` на
`/app/data`, затем `lms_uploads` на подкаталог `/app/data/uploads`; файлы
`storage-tmp` остаются в `lms_data`, uploads — в `lms_uploads`. Перемещение
временного файла из `storage-tmp` в `uploads` пересекает границу томов —
`dedup.ts` уже обрабатывает `EXDEV` через `copyFile` (это было верно и раньше,
когда корень был в `public/`).

## Процедура переезда прод-тома

Данные сохраняются: `lms_uploads` (на проде `learning_lms_uploads`) — named
volume, и правка меняет только точку монтирования (`/app/public/uploads` →
`/app/data/uploads`). Тот же том перемонтируется в новый путь, содержимое
переносится с ним; **имя тома не меняется**, файлы копировать не нужно.

Порядок на стенде/проде (применяет владелец инфраструктуры):

1. **Бэкап** тома до всего:

   ```bash
   docker run --rm -v learning_lms_uploads:/src -v "$PWD":/backup alpine \
     tar czf /backup/lms_uploads-backup.tgz -C /src .
   ```

2. `docker compose down` (Traefik-роутинг сохранится, том — тоже).
3. Выкатить新 compose (с `lms_uploads:/app/data/uploads`), `docker compose up -d --build`.
4. **Проверка**: залогиниться, открыть материал курса — файл отдаётся;
   анонимный `curl -I https://<host>/uploads/<любой-key>` → `401`.
5. **Откат** при проблеме: вернуть прежний compose
   (`lms_uploads:/app/public/uploads`) и `up -d` — том тот же, данные на месте.

Проверять на стенде (`TRAEFIK_TLS=false`) до прода.
