# ADR-002: серверный Assessment Engine

Статус: принят, 13 августа 2026.

## Контекст

Жизненный цикл теста находился внутри `course-actions.ts`, а новая попытка создавалась непосредственно при серверном рендере страницы. Обычный GET поэтому менял данные. Подсчёт баллов, лимиты попыток, задержка повтора, сохранение ответа и обновление лучшего результата выполнялись раздельно и не образовывали одной транзакционной границы.

Также правило прохождения содержало скрытое исключение: тест из десяти вопросов всегда требовал восемь правильных ответов независимо от настройки `minCorrectAnswers`.

## Решение

Создан модуль `src/modules/assessment` со слоями `domain`, `application`, `infrastructure` и `server`.

- Старт попытки выполняется только явным POST через Server Action.
- Открытие или предварительная загрузка страницы теста больше не расходует попытку.
- Старт, черновик и сдача используют один репозиторий с транзакционной границей.
- Итог и `QuizUserBestResult` сохраняются в одной транзакции.
- Ручная проверка повторно читает snapshot и ответы из БД, пересчитывает автоматическую и ручную части на сервере, затем атомарно обновляет попытку и лучший результат.
- Конкурирующие проверки защищены оптимистической версией `reviewedAt`: устаревшая форма не может затереть более новую оценку преподавателя.
- Сервер повторно проверяет число попыток, задержку повтора и лимит времени непосредственно перед записью. Для автоматической финальной отправки после `00:00` действует техническое окно 15 секунд; сохранение черновика после дедлайна запрещено.
- Порог прохождения определяется только `minCorrectAnswers` и ограничивается фактическим числом вопросов.
- Случайные вопросы и ответы фиксируются в snapshot попытки; последующее редактирование теста не меняет уже начатую работу.
- `src/lib/score-quiz.ts` и `src/lib/quiz-pass-rule.ts` оставлены временными совместимыми адаптерами для отчётов и ручной проверки.

## Граница доверия

React передаёт только ответы и события безопасности. Вопросы, правильные варианты, настройки попыток и порог прохождения загружаются сервером. Server Action выполняет аутентификацию и проверку доступа, а прикладной сценарий атомарно применяет правила попытки.

## Следующие шаги

1. Перенести сбор FormData и проверку файловых ответов в отдельный HTTP/server-action адаптер модуля.
2. Добавить ключ идемпотентности сдачи для безопасного повторного запроса после сетевого сбоя.
3. Вынести чтение результатов и статистики в query-сервисы модуля.
