# ADR-013: целевая архитектура и бэклог доведения

## Статус

Предложено, черновик (2026-08-25). Требует приоритизации с владельцем и сверки с Коляном
до крупных правок (пересечение по файлам).

## Контекст

За ADR 001–012 сложилась чистая основа: доменные модули `src/modules/` (learning, assessment,
enrollment, content, course, certification, outbox), у всех слои **domain / application /
infrastructure / server** (у outbox — без server, он вызывается инфраструктурой), транзакционный
outbox (ADR-005), read-side через `_queries/` (ADR-007), server action как транспорт (ADR-009), CI.

Замеры по коду (2026-08-25) показывают, чего «не успел» Колян — где основа есть, но не достроена:

- **Модули — «остров».** Из 26 файлов server actions **22 импортируют `prisma` напрямую**;
  в actions **69 бизнес-мутаций** (`create/update/delete/upsert/...`) против **37 внутри модулей**
  и 14 в `src/lib`. То есть ~⅔ записей идут мимо чистого паттерна — прямо в транспортном слое,
  вперемешку с бизнес-логикой. Это прямо противоречит ADR-009.
- **Раздутые файлы.** `courses/page.tsx` — 2006 строк (3 интерфейса в одном, находка IA-A);
  `page.tsx` — 1454 (2 дашборда, IA-B); несколько **action-файлов >1200 строк**
  (`user-actions` 1371, `course-survey-actions` 1264, `course-enrollment-actions` 1185) — раздуты
  именно потому, что логика лежит инлайн, а не в модулях.
- **Дыра в тестах.** По слоям: domain 14, application 10, lib 24, **infrastructure — 0**. Запросы
  и записи в БД (самое хрупкое) не покрыты.
- **Горячие точки запросов.** На страницу: `analytics` — 12 обращений к БД, `page` — 10,
  `users/[id]/edit` — 9. Требуют проверки на N+1 и индексы.
- **Открытый вопрос:** остаётся ли SQLite.

## Целевое состояние (правила)

1. **Server action — только транспорт** (ADR-009): guard → парсинг ввода → вызов use-case модуля →
   `revalidatePath`/`redirect`. Никаких `prisma.*`-мутаций с бизнес-логикой в actions.
2. **Любая запись — через модуль.** Use-case открывает свою транзакцию и атомарно пишет доменные
   изменения + `OutboxEvent` (ADR-005). Создание `OutboxEvent` — только в репозиториях модулей.
   Эталон уже есть: модуль `certification` (ADR-012).
3. **Чтение — через `_queries/`** рядом со страницей или read-порты модуля (ADR-007); сложные
   запросы не размазывать по компонентам.
4. **Каждый репозиторий покрыт тестом.** Инфра-слой: 0 → покрыть (моки Prisma или тестовая SQLite).
5. **Страница — тонкая.** Тяжёлая логика в `_queries`/модулях; гиганты разбиты по маршрутам/ролям.

## Бэклог (волнами, каждая — зелёные тесты/lint/build)

**Волна A. Вынести бизнес-логику из «толстых» actions в модули.**
Цель: `user-actions`, `course-survey-actions`, `course-enrollment-actions` (>1200 строк) → соответствующие
модули (user/survey/enrollment); action становится транспортом. Порядок — по числу мутаций и риску.
Побочно уменьшает файлы и даёт точки для тестов.

**Волна B. Инфра-тесты репозиториев** (0 → …). Начать с самых нагруженных: enrollment, learning,
assessment. Заодно фиксируют контракт портов.

**Волна C. Раскол гигантов** (пересекается с дизайн-D3 и с Коляном — сверять!):
`courses/page.tsx` 2006 → по маршрутам/ролям; `page.tsx` 1454 → role-based дашборд.

**Волна D. Оптимизация.** Проверить горячие точки (`analytics` 12 запросов, `users/[id]/edit` 9,
`page` 10) на N+1; добавить недостающие индексы; замерить до/после.

**Волна E. Решение по SQLite** — стратегическое, отдельно (см. ниже).

## Последствия и риски

- Крупные файлы (`courses`, дашборды) правит и Колян — до волн A/C сверяться через его PR
  (локального git нет; правило из CLAUDE.md про параллельные ветки).
- Выносы логики меняют внутренние контракты, не поведение — покрываются тестами до/после.
- Дизайн-миграция на примитивы идёт параллельно «по мере касания»: каждый экран, который трогаем
  ради A/C/D, заодно переводится на `src/components/ui`.

## Открытый вопрос: SQLite или Postgres

- **Оставить SQLite:** проще деплой (`db push`, ADR-010), меньше инфраструктуры; риск —
  сериализация записи и `SQLITE_BUSY` под нагрузкой, том на docker.
- **Перейти на Postgres:** конкурентная запись, масштаб; цена — переезд схемы, отказ от `db push`
  в пользу миграций, правка `Dockerfile`/compose, новый инфра-компонент.
- Решает владелец продукта; влияет на волну D и на стратегию деплоя.

**Разрешение (2026-09-02):** рекомендация — Postgres, план переезда вынесен в
[ADR-014](014-postgres-migration-plan.md). Профиль записи (веб + 4 воркера +
outbox на одном SQLite-файле общего тома) структурно не соответствует SQLite.
Волна D переосмыслена там же: значимого N+1 нет, индексы вносятся в состав
переезда (на PG дают эффект, на SQLite маргинальны).
