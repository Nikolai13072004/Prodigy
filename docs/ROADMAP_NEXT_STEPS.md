# Roadmap: Next Steps

Дата: 2026-04-21

Документ фиксирует ближайшие шаги после коммита `feat: expand HR reporting and automation workflows` и опирается на текущий код, [gap-analysis-admin-system.md](/home/team-02/lms-course3/docs/gap-analysis-admin-system.md) и состояние проекта на сегодня.

## Что уже есть

- Большой блок по HR-отчетам, выгрузкам и страницам учеников уже в `main`.
- Production-сборка проходит: `npm run build`.
- Для smoke-проверок добавлен минимальный e2e-контур на Playwright с отдельной тестовой SQLite-базой.

## Приоритет P0: стабилизация релиза

Цель: быстро снизить риск регрессий в уже реализованной отчетности.

- Прогонять `npm run test:e2e` перед следующими крупными изменениями в отчетах и ролях.
- Убрать или изолировать временные локальные артефакты, чтобы они не мешали качественным проверкам.
- Синхронизировать `README.md` и фактический сценарий деплоя из `docker-compose.yml`.

## Приоритет P1: аудит-лог действий администраторов

Почему сейчас:

- Это самый заметный функциональный разрыв из `gap-analysis`.
- Аудит-лог нужен как база для безопасного внедрения блокировок, удаления пользователей и массовых операций.

Scope:

- Prisma-модель для событий аудита.
- Запись событий для логина, управления пользователями, ролями, назначениями и экспортов.
- Экран фильтрации по дате, пользователю, типу действия.
- Экспорт CSV или JSON и простая политика хранения.

Критерий готовности:

- Администратор может понять, кто, когда и что изменил по ключевым объектам системы.

## Приоритет P2: CSV-импорт пользователей и приглашения

Почему следом:

- Это наиболее полезная административная доработка после отчетности.
- Импорт и приглашения убирают ручной ввод и ускоряют онбординг.

Scope:

- Загрузка CSV с предпросмотром.
- Валидационный отчет до применения.
- Обработка дублей по `login` и `email`.
- Email-приглашения или повторная отправка приглашения.

Критерий готовности:

- Администратор может массово завести пользователей без прямого редактирования БД.

## Приоритет P3: жизненный цикл учетной записи

Scope:

- Блокировка и разблокировка пользователя.
- Причина блокировки.
- Запрет удаления самого себя.
- Soft delete как безопасный первый этап вместо мгновенного hard delete.

Критерий готовности:

- Администратор может безопасно отключать доступ без потери истории и отчетности.

## Backlog после P3

- Экспорт платформенных данных целиком.
- Удаление кастомной роли с переназначением пользователей.
- Расширенные фильтры, пагинация и сортировка в списке пользователей.

## Рекомендуемый порядок выполнения

1. Закрыть P0 и стабилизировать уже добавленную отчетность.
2. Сделать аудит-лог как платформенный фундамент.
3. Поверх него внедрить CSV-импорт и приглашения.
4. Затем добавить блокировки, soft delete и остальные административные сценарии.
